# Prospect — Product Requirements Document (PRD)

**Version:** 0.1  
**Status:** Draft / MVP Planning  
**Product Type:** Financial Document Intelligence Platform  
**Working Name:** Prospect  
**Tagline:** Evidence-first financial research.

---

## 1. Product Overview

Prospect is an evidence-first financial document intelligence platform that transforms investment documents into structured, traceable financial information.

Users upload financial documents such as annual reports, financial statements, and prospectuses. Prospect processes the documents, extracts financial facts and tables, links extracted information to page-level evidence, performs transparent financial calculations, and provides source-grounded research assistance.

The core product principle is:

> **No claim without evidence.**

Prospect should not behave primarily as a "PDF chatbot." The application should maintain a deterministic financial data and evidence layer underneath its AI interface.

### Core flow

```text
Financial PDF
     ↓
Document Processing
     ↓
Text + Tables + Sections
     ↓
Structured Financial Facts
     ↓
Evidence / Provenance
     ↓
Deterministic Calculations
     ↓
Research Interface
     ↓
Grounded AI Interpretation
```

---

## 2. Problem Statement

Financial information is often distributed across lengthy annual reports, financial statements, and prospectuses.

A researcher may need to:

- locate specific financial figures;
- compare values across fiscal years;
- calculate financial ratios;
- identify material changes;
- understand management explanations;
- verify where a statement originated;
- navigate between an analytical answer and the original document.

Existing AI document interfaces can make retrieval easier, but they may obscure the distinction between:

1. facts directly reported by the document;
2. calculations derived from those facts;
3. interpretations generated by an AI model.

Prospect addresses this by making provenance and calculation transparency first-class parts of the system.

---

## 3. Product Vision

Prospect should become a research workspace where a user can move from:

**Document → Evidence → Financial Data → Calculation → Interpretation**

without losing the connection to the original source.

The long-term vision is to support multi-document financial research while keeping every material claim traceable to source evidence.

## 4. Goals

### Primary Goals

1. Extract useful financial information from investment documents.
2. Preserve page-level and section-level provenance.
3. Store extracted financial facts as structured data.
4. Perform deterministic financial calculations in the application layer.
5. Provide source-grounded question answering.
6. Allow users to inspect the evidence behind analytical claims.
7. Create a production-oriented architecture suitable for portfolio demonstration.

### Engineering Goals

- clear separation between document processing, data extraction, calculations, and AI;
- reliable financial data types and precision;
- asynchronous document processing;
- testable components;
- observable processing jobs;
- containerized deployment;
- extensible schema for future financial metrics.

### Portfolio Goals

Demonstrate practical experience across:

- backend engineering;
- financial software;
- data engineering;
- document processing;
- AI/RAG;
- relational databases;
- asynchronous systems;
- cloud deployment;
- testing and observability.

---

## 5. Non-Goals

The MVP will **not** attempt to:

- provide personalized investment advice;
- recommend securities to buy or sell;
- predict stock prices;
- automatically determine whether an investment is "good";
- replace professional financial analysis;
- process every possible financial document format;
- support every accounting standard from day one;
- train a custom foundation model;
- guarantee perfect extraction from arbitrary PDFs.

Prospect is a research and document intelligence tool, not an investment advisory service.

## 7. User Stories

### Document Ingestion

- As a user, I want to upload a financial PDF so that Prospect can process it.
- As a user, I want to see the processing status of my document.
- As a user, I want to know when a document is ready for research.
- As a user, I want failed processing jobs to provide a meaningful error state.

### Evidence

- As a user, I want every extracted financial fact to reference its source page.
- As a user, I want to open the source page from an analytical result.
- As a user, I want to distinguish reported facts from calculated metrics.

### Financial Analysis

- As a user, I want Prospect to extract common financial metrics.
- As a user, I want to compare financial metrics between years.
- As a user, I want Prospect to calculate common financial ratios.
- As a user, I want to inspect how a calculated value was produced.

### Research Chat

- As a user, I want to ask questions about a document.
- As a user, I want answers to cite relevant document pages.
- As a user, I want unsupported claims to be avoided.
- As a user, I want to inspect the evidence behind an answer.

## 8. Core Product Concepts

Prospect distinguishes three information classes.

### 8.1 FACT

Information directly extracted from a document.

Example:

```text
Revenue FY2025: Rp12.4T
Source: Annual Report 2025, page 87
```

### 8.2 CALCULATION

A value computed by Prospect from structured facts.

Example:

```text
Revenue Growth: +18.1%

Formula:
(Revenue 2025 - Revenue 2024) / Revenue 2024
```

### 8.3 INTERPRETATION

An explanation generated from evidence and/or structured calculations.

Example:

```text
Revenue increased by approximately 18.1% year-over-year.
The annual report attributes the increase primarily to...
```

The UI should visually distinguish these categories.

### Income Statement

- Revenue
- Gross Profit

- Net Income

- Total Assets

# 10. Functional Requirements

## FR-01 — Document Upload

The system shall allow users to upload supported PDF documents.

### Acceptance Criteria

- PDF files can be uploaded.
- Unsupported file types are rejected.
- File size limits are enforced.
- Uploaded documents receive a unique ID.
- The user receives processing status feedback.

---

## FR-02 — Document Processing

The system shall process uploaded documents asynchronously.

### Processing pipeline

```text
Upload
  ↓
Object Storage
  ↓
Processing Job
  ↓
PDF Parser
  ↓
Text Extraction
  ↓
Table Extraction
  ↓
Section Detection
  ↓
Financial Extraction
  ↓
Evidence Indexing
  ↓
READY
```

### Acceptance Criteria

- processing does not block the main request;
- status is persisted;
- failures are recorded;
- retryable failures can be retried;
- successful processing results in a READY state.

---

## FR-03 — Page-Level Evidence

Every extracted fact must maintain a reference to its originating document and page.

Example:

```json
{
  "document_id": "doc_123",
  "page": 87,
  "section": "Consolidated Income Statement"
}
```

---

## FR-04 — Financial Fact Extraction

The system shall extract supported financial metrics into structured records.

A financial fact must contain:

```text
Metric
Value
Currency
Unit
Period
Document
Page
Section
Confidence
```

---

## FR-05 — Financial Calculations

The calculation engine shall calculate supported metrics using structured financial facts.

The calculation engine must:

- use decimal-safe arithmetic;
- explicitly define formulas;
- retain input references;
- store calculation outputs;
- expose calculation provenance.

Example:

```text
Revenue Growth
Inputs:
  Revenue FY2024
  Revenue FY2025

Formula:
  (FY2025 - FY2024) / FY2024
```

---

## FR-06 — Evidence Viewer

Users shall be able to navigate from an extracted fact or AI answer to the relevant PDF page.

---

## FR-07 — Research Chat

The system shall answer questions using retrieved document evidence.

### Grounding rules

The assistant should:

1. retrieve relevant evidence;
2. use structured financial data where applicable;
3. cite relevant pages;
4. distinguish facts from calculations and interpretations;
5. avoid presenting unsupported claims as facts;
6. state when evidence is insufficient.

---

# 11. Non-Functional Requirements

## NFR-01 — Reliability

Financial calculations must be deterministic and reproducible.

## NFR-02 — Precision

Financial values should not rely on binary floating-point arithmetic where financial precision matters.

Recommended implementation:

```text
Python Decimal
PostgreSQL NUMERIC / DECIMAL
```

## NFR-03 — Traceability

Material analytical outputs must be traceable to source evidence.

## NFR-04 — Performance

Document processing should be asynchronous.

The UI should provide progress states rather than requiring a long-running synchronous HTTP request.

## NFR-05 — Security

The system should:

- validate uploaded files;
- isolate document storage;
- restrict document access to authorized users;
- avoid exposing storage credentials;
- apply API rate limits;
- sanitize extracted content before rendering.

## NFR-06 — Observability

The system should record:

- processing duration;
- processing failures;
- extraction failures;
- job status;
- API errors;
- LLM request failures.

# 17. Error Handling

Potential document-processing failures:

- corrupted PDF;
- scanned PDF;
- missing text layer;
- complex tables;
- rotated pages;
- unsupported encoding;
- OCR failure;
- extraction confidence below threshold.

The system should not silently invent or discard data.

Example:

```text
⚠ Some financial data could not be confidently extracted.

Page 112
Table: Consolidated Cash Flow Statement

[Review Page]
```

# 18. Security and Privacy

Financial documents may contain sensitive information.

The MVP should therefore include:

- authenticated document access;
- private object storage;
- signed / temporary file URLs where applicable;
- no public document URLs;
- deletion capability;
- clear data-retention behavior;
- secrets stored outside source control.

Future versions may include:

- encryption at rest;
- audit logs;
- organization-level access control;
- role-based permissions.

# 23. MVP Success Criteria

The MVP is considered successful when a user can:

1. upload a supported annual report;
2. see its processing status;
3. open the processed document;
4. navigate its pages;
5. retrieve supported financial metrics;
6. inspect the source page of each metric;
7. calculate supported financial ratios;
8. inspect calculation inputs;
9. ask a question about the document;
10. receive a source-grounded answer with page-level evidence.

The system does **not** need to support every financial document or every question to qualify as a successful MVP.

| Sensitive documents | High | Private storage + authentication |

# 26. Product Principles

### 1. Evidence Before Interpretation

The system should retrieve evidence before generating explanations.

### 2. Deterministic Before Generative

If a calculation can be performed by code, do not ask the LLM to perform it.

### 3. Traceability Over Convenience

A slightly slower answer with verifiable evidence is preferable to an impressive but unverifiable answer.

### 4. Structured Data Is a First-Class Citizen

The document should become structured financial information, not only embeddings.

### 5. Fail Explicitly

When extraction is uncertain, Prospect should communicate uncertainty rather than fabricate precision.

### 6. AI Is a Layer, Not the Foundation

The underlying document, evidence, data, and calculation architecture should remain useful even if the LLM provider changes.

# 28. First Development Milestone

The first milestone should **not** be an AI chatbot.

### Milestone: "First Evidence"

Given:

```text
Annual_Report_2025.pdf
```

Prospect must produce:

```text
Document
    ↓
Page 87
    ↓
Consolidated Income Statement
    ↓
Revenue
    ↓
FY2025 = X
FY2024 = Y
    ↓
Evidence references
```

Then the system calculates:

```text
Revenue Growth
= (X - Y) / Y
```

And the UI displays:

```text
Revenue
Rp X

Growth
+Y%

Source
Annual Report 2025 — Page 87
```

If this vertical slice works reliably, the rest of Prospect can be built incrementally around it.
